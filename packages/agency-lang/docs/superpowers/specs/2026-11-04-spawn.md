# `async`: run a call beside the rest of the block

The construct was drafted as `spawn`. It ships under the existing `async`
keyword; see "The keyword" below. The file name is kept so links to it keep
working.

Design notes and spike results: `docs/dev/language/fire-and-forget-notes.md`.
Spike branch: `spawn-spike` (worktree `worktrees/spawn-spike`).

## The problem

An agent often has work that should run while it produces its reply:
naming the conversation, extracting memories, compacting a thread. Today
that work either runs before the reply and delays it, or is left out. The
agency agent has memory extraction switched off for this reason.

Agency has `parallel` for running calls side by side, but it makes the
author restructure the block: every statement that should overlap with the
side call has to move into a `seq` arm. The old `async` keyword had the
shape people want, `let name = async f()`, but its runtime predates
concurrent interrupts and it cannot raise an interrupt from inside the call.
It is being removed.

## The keyword

`spawn` promises a detached task, which this is not, and it would reserve a
new word that collides with `node:child_process`. `parallel` as a prefix
reads as a one-arm block in value position, which is a different thing.
`async` already has this exact surface in the language and is already
reserved. Its one cost is the "pair it with `await`" habit from other
languages; Agency has no `await`, and the value is ready when it is read.
Old `async` programs keep compiling and get the new semantics.

## The decision

`async` is syntax for a `parallel` block. It adds no runtime semantics of
its own. The side call runs as one fork arm, and the statements after it,
up to the join, run as the other arm. The main request waits for the side
request at the join. Every property of fork carries over: interrupts from
either arm are batched and resumable, handlers that enclose the block apply
to both arms, and the checkpoint is always complete.

The alternative, a task with its own checkpoint that the parent does not
wait for, was worked through and rejected. Each thing fork gives for free
(enclosing handlers, branch state, thread ownership, argument aliasing,
restore) needed its own rule for a detached task. The notes file has the
table.

## Syntax

Two forms.

```agency
async extractMemories(thread)
```

```agency
let name = async nameConversation(userMessage)
```

`async` takes one call: a function call, a method call, or an `llm()` call,
with an optional `with approve` or `with <handler>` suffix on the call. It
is a statement or the right-hand side of a `let` or `const`. It is not an
expression: `foo(async f())` is a compile error.

## Where the join is

The join is the point where the main arm ends and the side call's value
is required.

- For `let x = async f()`, the join is just before the first statement that
  mentions `x`, or the end of the enclosing block if nothing does. A mention
  anywhere inside a statement counts, including inside a nested `if`, a
  loop body, a lambda, or an assignment to `x`.
- For the bare statement form, the join is the end of the enclosing block.
- In both forms, the join never falls after a top-level `goto`, `break`, or
  `continue` in the block. It moves to just before the first one, so a node
  that ends in `goto` and a loop body that ends in `continue` can use either
  form.

The enclosing block is the body the `async` statement sits in: a function
or node body, an `if` branch, a loop body, a `handle` body, a `seq` arm.

Two `async` calls in one block nest. The calls lower from first to last, so
the second call sits inside the first call's arm, and its join is bounded by
that arm: it may come earlier than the second value's first use. The value
is still correct; the only effect is less overlap.

## Lowering

The preprocessor rewrites

```agency
let name = async nameConversation(msg)
const reply = llm(msg)
print(reply)
print(name)
```

into

```agency
const __async_arg_0 = msg
parallel(shared: true) {          // origin: "async"
  let name = nameConversation(__async_arg_0)
  seq {
    const reply = llm(msg)
    print(reply)
  }
}
print(name)
```

which the existing `parallelDesugar` turns into a `fork`:

```agency
const __async_arg_0 = msg
let __arms_0 = fork(["arm_0", "arm_1"], shared: true) as __arm_0 {   // mainThread: 1
  if (__arm_0 == "arm_0") {
    let name = nameConversation(__async_arg_0)
    return { name: name }
  }
  if (__arm_0 == "arm_1") {
    const reply = llm(msg)
    print(reply)
    return __asyncDone({ reply: reply })
  }
}
if (!__asyncFinished(__arms_0[1])) {
  return __arms_0[1]
}
let name = __arms_0[0].name
let reply = __arms_0[1].reply
print(name)
```

Bindings made in the `seq` arm are hoisted after the block the way `parallel`
already hoists them, so `reply` is in scope after the join.

The new pieces:

**The argument temporaries.** The side call's receiver, its callee when that
is a function value in a local, and each argument that names anything are
copied into temporaries before the block, so `async f(n)` reads `n` at the
`async` line, as a plain call would. Without them the side arm reads them
inside its first step, and the main arm's `n = 2` could land first.

**`mainThread: 1`** marks the `seq` arm as the one that writes to the
parent's active thread. It is a field the lowering sets on the fork node,
not something a user can type. Without it the main arm's `llm()` messages go to a
subthread and the conversation loses its own reply; the spike proved both
halves. The side arm keeps a branch-local subthread, so its model calls stay
out of the conversation.

**`shared: true`** keeps globals shared between the arms, because a plain
call and the code after it share globals today. The side call can race the
main arm on a global, which is the same situation as two tool calls in one
model round.

**Returns.** A `return` inside the `seq` arm returns from the arm. The
lowering does not rewrite returns. The arm ends with a marked completion,
`__asyncDone({ ... })`, and the join check returns any other arm value from
the enclosing function. That covers returns at any depth, a bare `return`,
the `return` statements the hoist pass writes later for `?`, and an
interrupt rejected directly in the arm.

## Compile errors

- A `goto`, `break`, or `continue` nested inside the arm below its top
  level, and not inside a loop that is itself in the arm. Neither can cross a
  fork; the spike showed the runtime crashing on a `goto` in a branch. A
  top-level one ends the arm instead (see "Where the join is"). An `async` in
  a loop body is otherwise allowed, and each iteration joins at the end of
  its body.
- `async` in expression position.
- `async` at module top level, in global initialization, inside a handler
  function, or inside a callback body. Fork is not available there either.
- `async` as a direct arm of a `parallel` block.
- `?` on the async call itself. Unwrap the value after the join.
- `async` of anything that is not a call.

## Types

The typechecker sees `async` before the lowering. `let x = async f()` gives
`x` the return type of `f`, with `!` and `with` suffixes handled as they are
on a plain call.

## Semantics to document for users

- The main request waits for the side request at the join. A slow side
  call delays the reply by the difference.
- An interrupt in either arm is batched with any interrupt from the other
  arm and waits for the other arm to settle before it surfaces. This is
  fork's behaviour.
- An interrupt in the side call means the node is not done until the user
  answers.
- A handler inside the side call applies to the side call only, and a
  handler around the whole block applies to both arms. The same holds for a
  `preapprove()`d function.
- The first interrupt in the main arm surfaces only after the side call has
  settled; later ones surface at once.
- An early `return` in the main arm waits for the side call too. The side
  call never outlives the function, so a turn that can exit early should
  start its async calls after its early exits.
- A pause requested during an async block lands after the block, and the
  debugger's `set` is refused inside it.
- The side call's `llm()` starts from a copy of the conversation so far;
  `thread { }` inside it gives a blank one.
- A call in the async call's arguments runs before the overlap:
  `async f(llm(prompt))` makes that `llm()` call first.
- A side call written in TypeScript that throws ends the turn and drops a
  pending prompt.
- Under a decision-model provider the two arms' calls share rounds.
- The side call's model messages stay off the conversation thread.
- Globals are shared between the arms.
- The trace shows the main arm as a fork branch.

## What the spikes showed

| Question | Answer |
|---|---|
| Do the main arm's model messages reach the conversation? | Not with fork as is. Yes with the per-branch `mainThread` option, across an interrupt and resume. |
| Does `endTurn()` work from a tool inside an arm? | Yes. |
| Does `goto` work inside an arm? | No, it crashes checkpoint serialization. Compile error. |
| Does `return` inside an arm leave the function? | No, only the arm. The join check returns it from the function. |
| Does the main arm's interrupt resume with the side arm cached? | Yes, fork's existing behaviour. |
| Do enclosing handlers apply inside both arms? | Yes, fork's existing behaviour. |
| Does an object mutated by one arm stay shared after resume? | Yes, both arms read it through the parent frame. |

## Out of scope

- Deleting the old `async` runtime (pending promises). A separate change;
  see the plan.
- Pausing a run while an arm is still running (#1046). The join semantic
  makes it unnecessary for this feature. As a consequence, an external
  pause requested during an async block waits for the join.
- Letting the node return before the side call finishes. If that is wanted
  later, the host-level pattern is to start the side work as its own run
  from TypeScript after the node returns.
