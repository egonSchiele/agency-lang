# Attaching the debugger to a running program

The design is `docs/superpowers/specs/2026-10-20-attach-to-a-running-program.md`. This doc records what shipped and the parts that are easy to get wrong. The runtime half, a driver installed on a program something else is running, is the section "A debugger installed on a running program" in `debugger.md`; this doc is the channel, the trigger, and the socket. The `agency debug --attach` command is a later PR and will be described here when it lands.

## The pieces

- `lib/debugger/attach/channel.ts`: the `Channel` type (`send`, `onMessage`, `onClose`, `close`) and `memoryChannelPair()` for tests.
- `lib/debugger/attach/protocol.ts`: the messages, as zod schemas. One `request` per `DebuggerIO` method that expects an answer, with an id the `reply` carries back; one `notice` per method that returns at once (`log`, `setMode`, `setOverrides`, `appendStdout`, the spinner); and three that are not methods: `hello` from the run when a debugger connects, `finished` when the program ends, and `refused` when a debugger is already attached. There is no detach message: closing the channel, from either side, is the detach. `REPLY_SCHEMAS` says what each request's reply must carry.
- `lib/debugger/attach/channelIO.ts`: `ChannelDebuggerIO`, the run side's `DebuggerIO`. A call waiting for a reply when the channel closes is rejected with `DebuggerDetached`, which the attached driver treats as `continue`. A reply that carries the UI's error, or a result that fails its method's schema, ends the session the same way, with one line on the program's stderr saying why: a program must never fail because its debugger did, and before this rule a terminal UI that hit a bug while drawing a checkpoint took the agent down with it.
- `lib/debugger/attach/serveIO.ts`: `serveDebuggerIO(channel, io, events)`, the UI side, which answers each request with the matching call on a real `DebuggerIO`, the terminal UI or a scripted one in a test. `checkpointFromWire` sets an empty function-ref registry before reviving, because the debugger's process loads no compiled module and only a module sets one; a function value in a frame then revives to the stub a registry miss gives, which is all a UI that shows the state needs.
- `lib/debugger/attach/lineChannel.ts`: a channel over a Node socket, newline-delimited JSON with a 64 MiB cap per message. A message is kept as the pieces it arrived in and joined once at its newline, since scanning the whole buffer on every chunk made a 60 MiB message take half a minute; the cap is checked per line, and per partial line as it grows. A message over the cap, sent or received, closes the session with a line on stderr. `close` ends the socket and destroys it once the writes have gone out, with a short fallback, because destroying right after `end` threw away a `finished` message over about 8 KB.
- `lib/debugger/attach/registry.ts`: the sessions directory and its records.
- `lib/debugger/attach/server.ts`: `attachOverChannel`, which is all of attaching once a channel exists, and `startAttachServer`, the socket around it. The server takes the functions as a getter and reads it when a debugger connects, so the context running then is the one attached to; a TypeScript program can have started another module's node since the signal arrived.
- `lib/runtime/attachedDebugger.ts` also holds `attachFunctionsFor(ctx)`: the four functions a driver takes, bound to a context, for the server that runs inside the program and has no module to ask. They are bound in the runtime that owns the context and handed to `registerAttach`, because the `#platform` file can be a different copy of the runtime than the one the program imported: a test loads the program's copy through vite and the platform file through Node, and a copy that did not load the program's modules fails the fingerprint check on resume.
- `lib/runtime/platform.node.ts`: `registerAttach`, called by `runNode`.

## What crosses the channel

A checkpoint crosses as `checkpoint.toJSON()` run through `nativeTypeReplacer`, the way `debugStep` prepares the `onCheckpoint` payload, and comes back through `nativeTypeReviver` and `Checkpoint.fromJSON`. The rewind selector and the checkpoints panel are sent the whole window of checkpoints, not summaries: both show the state at each checkpoint as the selection moves, so a summary would not do. They are sent only when the person opens the panel, and the per-message cap is sized for them. `DebugStopData`, `GuardTripData`, `DebuggerCommand`, and `InterruptResponse` are plain data already.

## Registration

`runNode` calls `registerAttach({ ctx, nodeName, host, functions })` on every node run, with the host the run uses (the invocation's when it names one) and the driver functions bound to the context. The record and the signal listener are written once per process, by the first node run; a later run only makes its context the one a debugger attaches to, since a TypeScript program that imports two Agency modules, or a test worker that runs many fixtures, has several contexts in one process and the one running now is the one a person attaching now means. The call returns at once when: the host is not the Node host, so a memory host in a test writes nothing; a debugger is already installed, so `agency debug` does not register its own process and a second debugger cannot attach over the first; or the process is an IPC child of a parent Agency program (`isIpcMode(host)`, which reads `AGENCY_IPC`, set by the parent; a test worker also has an IPC channel to its runner, so the channel alone would not do), which the listing leaves out. `runNodeForServe` does not call it, so a serve never registers: one serve process runs many invocations at once and one shared `DebuggerState` would stop them all. A directory that was refused is remembered, so a program that runs a node in a loop pays the check and the log line once.

Registering writes `<pid>.json` in the sessions directory and installs a `SIGUSR2` listener. The listener is kept in one slot on `process` (a symbol), and every registration claims the slot: a process can hold more than one copy of the runtime (a test worker re-evaluates modules per file; a program can have the package twice under `node_modules`), each with its own attach target, and two listeners would start two servers racing for one socket, the loser answering with a context whose modules it cannot see. Claiming on every registration, not only the first, means copies that register A, B, A leave A's listener in place. Node reserves `SIGUSR1` for its own inspector, whose port any local user can reach, so Agency does not touch it; `nodemon` restarts a child with `SIGUSR2`, which a program under `nodemon` then no longer honours. The record holds the pid, the program path from `process.argv[1]`, the first node run, and the process start time as `Date.now() - process.uptime() * 1000`, read without a child process. A sessions directory that cannot be used is logged under `DEBUG` and the run goes on without attach: a program must never fail because it cannot be debugged. The record and the socket are removed in `host.system.onExit`.

## The sessions directory

`~/.agency/debug-sessions`, or `debug-sessions` under `AGENCY_HOME`, which test setup points at a temporary directory. `~/.agency` is Agency's own per-user directory (`agencyHomeDir`), not the agent home: `~/.agency-agent` belongs to the built-in `agency agent`, and attach is for any program.

Whoever can connect to the socket can do what the program's owner can do, so the directory is treated as a credential. `ensureSessionsDir` creates it with mode `0700` and refuses it unless the current user owns it and no group or world bits are set. The run checks at registration and again in `startAttachServer`, right before `listen`, since the signal can come hours after registration and the directory can have been replaced in between; the CLI checks on every use. That check is what the safety argument rests on. The socket is also `chmod 0600` after `listen`, a second layer with a short window at the umask's mode, which is why the directory check comes first. `fs.mkdirSync` applies a mode only to a directory it creates, so a directory left by an earlier build keeps whatever mode it had, and the check tells the person to `chmod 700` it. A record is written with `wx` after removing the path, so a symlink left at `<pid>.json` is replaced rather than followed, and a record is read only when the pid inside matches its file name, so a hand-edited file cannot point the CLI at another process.

## The socket

`startAttachServer` listens on `<pid>.sock`, removing a leftover socket at its own pid's path first (a run that exited through a signal handler leaves one, and a reused pid would hit `EADDRINUSE` on it), and refuses on Windows and on a path over 104 bytes, the limit on macOS and the BSDs. Every failure, including a directory at the socket's path that the removal cannot take, comes back as `unavailable` and one line on stderr: the function is `async` so nothing it does can throw into the signal listener, where a throw would end the program. The server and every accepted socket are `unref`ed, so an open session never keeps a finished program alive; the run side's `ChannelDebuggerIO` `ref`s the socket while a request is pending (`Channel.keepAlive`), because a program stopped at a debug stop is waiting on the debugger's answer and may hold no other handle, and with the socket unreferenced Node would exit with code 13, an unsettled top-level await. The end-to-end test in the command's PR found that. The first connection gets `hello` and a driver; a second while one is attached gets `refused` with "already attached since <time>" and is closed, since Node cannot read the peer's pid from a Unix socket. When the channel closes for any reason the driver detaches, and when the program finishes while attached the run sends `finished` and closes. The driver's last render, at the end of the program, is sent and not waited for: at a stop, waiting on the debugger is what the person asked for, but a debugger suspended with Ctrl-Z must not keep a finished program from exiting.

## Tests

`channel.test.ts` (the memory pair and the line channel on a real socket: the cap, two messages in one chunk, and the last message before a close), `attach.test.ts` (a scripted IO on a memory pair, including a UI that throws and a reply of the wrong shape, a checkpoint with a function value rebuilt with no registry, and the real path: `runNode` registers the test process, the signal handler is called the way the signal would call it, and a client on the socket drives the program), `registry.test.ts`, `server.test.ts` (including the getter naming a second context), and the `registerAttach` cases in `lib/runtime/platform.test.ts`. Every unit test worker runs with `AGENCY_HOME` pointed at a temporary directory it removes on exit (`lib/debugger/attach/vitest.setup.ts`, listed in `vitest.config.ts`), because every program a test runs on the Node host registers, and the real `~/.agency` must never see a test's records. The children `agency test` starts get the same throwaway directory as their `AGENCY_AGENT_HOME` sandbox.
