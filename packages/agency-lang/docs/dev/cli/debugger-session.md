# `agency debug session`: the debugger an agent drives

The design is `docs/superpowers/specs/2026-10-20-agent-debug-session.md` and the plan `docs/superpowers/plans/2026-10-21-agent-debug-session.md`. This doc records what shipped and the parts that are easy to get wrong. The run side, a session the run holds between visits and two parties on one run, is in `debugger-attach.md` ("A session with parties" and "Two parties, one answer"); this doc is the CLI. The user's view is in `docs/site/cli/debug.md`.

## The pieces

`lib/cli/debugSession/`, on the pattern of `lib/cli/logsSession/`:

- `visit.ts`: one connection to a program's debug socket as a `cli` party. It keeps the latest `setPending` notice as `queuedEdits`, read live through a getter, so the `where` a verb prints after queuing an edit shows it; the session replays the notice to a joiner, so a later visit prints the `edits` line too. `openVisit` sends `client cli` and collects what the run sends a party as it joins: `hello`, `parties`, the recent activity lines as `log` notices, the last `render`, and the request waiting for an answer. A render is acknowledged as it arrives, as a UI would, and kept as `shown`; a render with no checkpoint is the same stop redrawn (the driver sends one after `set` and `checkpoint`), so the checkpoint already shown stays, as the terminal keeps its own. Everything else lands in an inbox the commands read from, and what has already arrived is taken whatever the deadline, so a zero wait still sees a refusal that came with the reply. The one thing the run does not say is "that is all": the stop and the pending request follow `parties` at once when the program is stopped, and nothing follows when it is running, so after `parties` the visit waits `JOIN_GRACE_MS` for a request before deciding the program is running. `answer` sends the one reply a command decides on and waits for what comes next: the next request (with the render before it), `answered` (another party got there first), `finished`, the channel closing, or the deadline. `probeStatus` is the `probe` handshake for `list`. The one bug this file had: the probe resolved its promise after closing the channel, and the close listener's `null` won, so every listing said `none`; a promise keeps its first value, so the resolve comes before the close.
- `readers.ts`: pure functions of a `Checkpoint` and the stop, over the `Checkpoint` methods the terminal's panes read too (`framesAlong`, `listThreads`, `listBranches`, `listGuards`, `loopState`), so the two views cannot drift; `frame` with no number picks the frame the terminal shows, which at one of the tool loop's own stops is the caller under the loop's frame. `readSourceMap` reads the compiled program's `__sourceMap` from the file as text: the CLI never loads the program's code (the UI side's import of it is the problem `debugger-future-work.md` lists), and the map's layout depends on the compile (one line under the test compile, many under the run strategy), so it is found by its opening brace and read to the matching one, strings skipped (`objectLiteralAfter`). `lineFor` is the UI's lookup; `sourcePathFor` looks under the current directory and beside the compiled program.
- `where.ts`: the one-screen summary, one pure function of what the visit was shown, to text and to JSON. The empty main thread of a program that has not called the model is left out.
- `commands.ts`: one function per verb, of a `Visit`, its arguments, and the program's record, to `{ text, json, exitCode }`. A reader prints from `visit.shown`. A moving verb answers the pending request and prints `where` at the stop that follows, the refusal when another party answered first, the program's end, or that it is running; `continue` waits only `ANSWER_GRACE_MS` for a refusal, since the program may run for an hour. A stop that follows is not a success by itself: the driver logs one line when a command could not be done (`back` at the earliest checkpoint, a `save` that fails, `set` where it is not supported), and the lines in `FAILURE_LINES` make that stop a refusal carrying the driver's words. `set` prints the frame of the stop the set redrew, read from what the move returned, never from the `Visit` fields, which are what the visit was shown when it joined and do not change. `answer` replies to a question the program is waiting on (a guard trip, a node's arguments, `input()`), checking the value against `REPLY_SCHEMAS` first, since the run drops a visit that answers with the wrong shape. `checkpoints` and `rewind` are two-step: the stop is answered with `showCheckpoints` or `rewind`, the driver asks the visit to show the panel or the picker, and the visit prints the list or picks by id. `detach` sends the `detach` message, which releases the CLI's hold; it says the program runs on only when no terminal is attached, since with one the program stays at its stop for the person. `edit` is the verbs over the debugger's action table (`docs/dev/cli/debugger.md`, "Edits on the rows"): with no action it lists the edits this stop takes, each with its choice flag (`--thread`, `--name`, `--guard`, `--branch`), the choices read from the checkpoint (a label before an id or index, since that is what a person copies, and either is accepted), and the default in brackets; with an action it finds the row from the flag, builds the edit through the table's `toEdits`, sends it as the `edit` command through `sameStop`, and prints the applied lines the driver logged, or the driver's `refused:` line as a refusal (the line is in `FAILURE_LINES`); `--drop` sends `dropEdits`. The verb never names an edit: a row added to the table is a verb at once.
- `editVerb.ts`: the tables that turn a row kind into a flag (`CHOICE_FLAGS`) and what an action asks for into a flag (`ASK_FLAGS`), the listing (`listEdits`, `listingText`), and `editsFor`, the request to edits; `viewOf` builds the table's `StopView` from what the visit was shown.
- `target.ts`: which program a command acts on: `--pid`, else the one run that holds a session, else a refusal that says what to do. `sessionWords` is the `SESSION` column. A program whose socket answers with no session at all is listening for a debugger, not being debugged, and only `attach` may open a session on it: every other verb is refused there, since a visit would stop the program.
- `index.ts`: the sequence: the sessions directory check, the records, a probe per live socket, the target, the connection, the visit, the verb, the print. The only file here with a socket in it. The run learns a visit is over from its socket closing, which lands a moment after the command's process exits, so a script running commands back to back can be refused as a second visit; a command refused that way retries its join for `VISIT_RETRY_MS`. (Waiting on the channel's own close listener does not help: `lineChannel.close` runs its listeners at once, before the peer has seen anything.) JSON goes to stdout whatever the exit code, so a program reading it finds a refusal where it reads everything else; text refusals go to stderr.
- `register.ts`: `session` under `debug`, one leaf per verb, `--pid` and `--json` on each leaf (the vendored commander refuses a flag an ancestor declares). `debug` keeps its own `[file]` argument and action beside the subcommand, as `logs` does.

The exit codes: 0 an answer, 1 a refusal (on stderr, with the way forward), 2 the program ended, 3 `wait` ran out.

## The one invariant

A command is one visit and one reply, and the run owns everything between. No verb keeps state on the CLI across two connections, which is what keeps two parties on one run a matter of "first reply wins" and never of merging. `checkpoints` and `rewind` make two replies in one visit, which is still one visit.

## Tests

`where.test.ts` (the summary and the readers on a checkpoint the driver drew for the step-test fixture, sent over the wire and rebuilt as the CLI gets it; the source map read from the compiled file; the brace scanner), `commands.test.ts` (the verbs on a scripted visit: the refusals, the stale answer, the exit codes; the target rules; the session column), and `index.test.ts` (the whole path against a program in another process over a real socket, as `lib/cli/attach.test.ts` does: `list`, `attach`, `where`, `stack`, `frame`, `step`, `continue`, `wait` to the end, and `detach`). `server.test.ts` has the probe before and after a visit.
