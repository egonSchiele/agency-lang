# `agency debug session`: the debugger an agent drives

The design is `docs/superpowers/specs/2026-10-20-agent-debug-session.md` and the plan `docs/superpowers/plans/2026-10-21-agent-debug-session.md`. This doc records what shipped and the parts that are easy to get wrong. The run side, a session the run holds between visits and two parties on one run, is in `debugger-attach.md` ("A session with parties" and "Two parties, one answer"); this doc is the CLI. The user's view is in `docs/site/cli/debug.md`.

## The pieces

`lib/cli/debugSession/`, on the pattern of `lib/cli/logsSession/`:

- `visit.ts`: one connection to a program's debug socket as a `cli` party. `openVisit` sends `client cli` and collects what the run sends a party as it joins: `hello`, `parties`, the recent activity lines as `log` notices, the last `render`, and the request waiting for an answer. A render is acknowledged as it arrives, as a UI would, and kept as `shown`; everything else lands in an inbox the commands read from. The one thing the run does not say is "that is all": the stop and the pending request follow `parties` at once when the program is stopped, and nothing follows when it is running, so after `parties` the visit waits `JOIN_GRACE_MS` for a request before deciding the program is running. `answer` sends the one reply a command decides on and waits for what comes next: the next request (with the render before it), `answered` (another party got there first), `finished`, the channel closing, or the deadline. `probeStatus` is the `probe` handshake for `list`. The one bug this file had: the probe resolved its promise after closing the channel, and the close listener's `null` won, so every listing said `none`; a promise keeps its first value, so the resolve comes before the close.
- `readers.ts`: pure functions of a `Checkpoint` and the stop's branch path, over the `Checkpoint` methods the terminal's panes read too (`framesAlong`, `listThreads`, `listBranches`, `listGuards`, `loopState`), so the two views cannot drift. `readSourceMap` reads the compiled program's `__sourceMap` from the file as text: the CLI never loads the program's code (the UI side's import of it is the problem `debugger-future-work.md` lists), and the map's layout depends on the compile (one line under the test compile, many under the run strategy), so it is found by its opening brace and read to the matching one, strings skipped (`objectLiteralAfter`). `lineFor` is the UI's lookup; `sourcePathFor` looks under the current directory and beside the compiled program.
- `where.ts`: the one-screen summary, one pure function of what the visit was shown, to text and to JSON. The empty main thread of a program that has not called the model is left out.
- `commands.ts`: one function per verb, of a `Visit`, its arguments, and the program's record, to `{ text, json, exitCode }`. A reader prints from `visit.shown`. A moving verb answers the pending request and prints `where` at the stop that follows, the refusal when another party answered first, the program's end, or that it is running; `continue` waits for nothing, since the program may run for an hour. `checkpoints` and `rewind` are two-step: the stop is answered with `showCheckpoints` or `rewind`, the driver asks the visit to show the panel or the picker, and the visit prints the list or picks by id. `detach` sends the `detach` message, which releases the CLI's hold.
- `target.ts`: which program a command acts on: `--pid`, else the one run that holds a session, else a refusal that says what to do. `sessionWords` is the `SESSION` column.
- `index.ts`: the sequence: the sessions directory check, the records, a probe per live socket, the target, the connection, the visit, the verb, the print. The only file here with a socket in it. A command waits for its visit's socket to close before it returns, because the run learns a visit is over from the close, and a script running commands back to back would otherwise find the last one still connected and be refused as a second visit.
- `register.ts`: `session` under `debug`, one leaf per verb, `--pid` and `--json` on each leaf (the vendored commander refuses a flag an ancestor declares). `debug` keeps its own `[file]` argument and action beside the subcommand, as `logs` does.

The exit codes: 0 an answer, 1 a refusal (on stderr, with the way forward), 2 the program ended, 3 `wait` ran out.

## The one invariant

A command is one visit and one reply, and the run owns everything between. No verb keeps state on the CLI across two connections, which is what keeps two parties on one run a matter of "first reply wins" and never of merging. `checkpoints` and `rewind` make two replies in one visit, which is still one visit.

## Tests

`where.test.ts` (the summary and the readers on a checkpoint the driver drew for the step-test fixture, sent over the wire and rebuilt as the CLI gets it; the source map read from the compiled file; the brace scanner), `commands.test.ts` (the verbs on a scripted visit: the refusals, the stale answer, the exit codes; the target rules; the session column), and `index.test.ts` (the whole path against a program in another process over a real socket, as `lib/cli/attach.test.ts` does: `list`, `attach`, `where`, `stack`, `frame`, `step`, `continue`, `wait` to the end, and `detach`). `server.test.ts` has the probe before and after a visit.
