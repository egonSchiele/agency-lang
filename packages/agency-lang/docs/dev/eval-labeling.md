# The human-label store

`agency eval label` builds a dataset of human judgements about agent outputs.
This page is about the parts that are easy to get wrong: what identifies what,
which order writes happen in, and why validation here is stricter than anywhere
else in the eval framework.

## Why the store is outside `runs/`

Runs are disposable. The dataset is not.

Every other eval artifact can be regenerated by re-running an agent. A human
judgement cannot: it took someone's attention, and the only copy is the one on
disk. So the store lives outside `runs/` (default `labels/`, configurable as
`eval.labelStore`), and it holds **copies** of the outputs it labels rather
than pointers into a run directory. Deleting `runs/` must never destroy
labels.

This matches what observability platforms do — trace retention is measured in
days, dataset retention is indefinite, and promoting a trace into a dataset
copies it.

## Identities

Getting this list wrong is how a dataset silently stops meaning what it says.

| Identity | Names | Rule |
|---|---|---|
| `outputId` | One captured **occurrence** | `sha256` of `(traceId, inputId, finalOutputIndex)`. Never a path |
| `contentHash` | The **content** | `sha256` of `(input, value)`. Deduplication and search only — never identity |
| `checklistId` | A checklist **lineage** | `name` is display metadata |
| `checklistVersion` + `checklistHash` | One immutable **revision** | Every revision is a full snapshot |
| `questionId` | One question's **meaning** | Changing text needs a new id. Never reused |
| `annotationId` | One sign-off event | Generated before the write, so a retry is idempotent |
| `annotator` (`kind` + `id`) | Who judged | A machine `id` identifies one judge configuration and revision |
| `sessionId` | One resumable session | `sha256` of ordered `outputIds`, `checklistId`, annotator |

**Occurrence, not content.** Two runs of the same input are two outputs worth
keeping, so identity cannot be a hash of the text. Text alone is also
insufficient: `"Looks good"` means different things under "Review this patch"
and "Write a release announcement", `Input.task` can be an object, and an
output value can be structured JSON.

**Never a path.** A run directory can be renamed or copied, and two unrelated
runs can share a basename. `traceId` is persisted in the eval record and does
not move.

**Order is part of the session identity.** Answers are stored by output id but
the cursor is an index. A draft resumed against a reordered source would put a
person in front of a different output than their position implies, so a
reordered source hashes to a different session.

## The three state machines

### 1. Source occurrence capture

`inspect → skip or identify → replay or conflict → append → ordered result`

Eligibility is narrow, and every rejection is reported with a code rather than
dropped:

| Reason | Why it is not labellable |
|---|---|
| `run-failed` | A failed run's salvaged record is evidence for diagnosis, not a result to judge — the same reason grading refuses it |
| `record-unreadable` | Nothing to read |
| `legacy-record` | Predates recorded eval outputs; there is no way to say which output was final |
| `missing-trace-id` | No stable identity across recapture |
| `invalid-task` | The task is missing or not JSON data |
| `no-output` | Filesystem-oriented runs legitimately produce none |
| `truncated-output` | A label on a truncation is not a judgement of the output |

A placeholder in the corpus would be worse than a gap, because a placeholder
can be labelled.

Selection returns the chosen **index** alongside the value, so identity and
display can never disagree about which output was judged. The text projection
matches `lib/eval/judge/selectFinalResponse.ts`: strings pass through,
everything else is JSON. `String(value)` would render an object as
`[object Object]` and merge unrelated structured outputs into one meaningless
string.

Recapturing the same run is idempotent. Reusing an output id with different
content is refused — a rewritten record or a reused trace id would otherwise
drift existing labels onto different text. `capturedAt` and provenance are
excluded from that comparison, because they can differ between two captures of
the same execution without changing what was judged.

### 2. Checklist publication

`staged → pending in draft → immutable snapshot → current advanced → draft rebound → pending cleared`

Every revision is a complete immutable snapshot at
`checklists/<checklistId>/<version>.json`, with `current.json` as a small
pointer rather than a second copy. A mutable file with an incrementing integer
could not reconstruct what version 3 contained once version 4 existed, and
annotations name a version — later agreement measurement has to reproduce the
exact rubric a person used.

An external checklist file resolves to one of four outcomes:

- **current** — unchanged; nothing to do.
- **publish** — a legal change against current: add a question, soft-delete
  one, restore one, or change a weight.
- **refresh-definition** — the file is behind current but unedited, so it is
  brought up to date.
- **refusal** — the file is behind current **and** edited. This is ambiguous:
  publishing it would discard whatever landed in between, and there is no safe
  automatic answer.

Illegal at any time: changing a question's text under the same id (it would
silently change what past answers meant), removing a question (it would strand
its answers), a non-positive weight, or claiming a version ahead of the store.

### 3. Session recovery

`lock → validate → capture → bind draft → recover revision → recover annotation → overlay → active → close`

Revision before annotation, because an annotation names the revision it was
made against and must never reference one that is not durable yet.

## The sign-off commit protocol

Sign-off touches several files, so the order is owned by `controller.ts` alone
and no other caller may reproduce it.

1. Flush and persist accumulated timing, without marking reviewed or advancing.
2. If questions are staged, save the complete pending revision in the draft.
3. Publish the revision (immutable file, then current pointer, then the
   external definition) — one store operation, so those three steps cannot be
   split.
4. Rebind the draft to the new version and clear the pending revision.
5. Build and validate the annotation against that durable revision, covering
   every live question, writing an untouched checkbox as explicit `false`.
6. Save the complete row as `pendingAnnotation` **before** appending it.
7. Append or replay through the store facade.
8. Reduce `annotationCommitted`: mark reviewed, advance, reset this output's
   timer for a later relabel.
9. Save the post-commit draft.

Every step is idempotent, so reopening after a crash at any boundary converges
on exactly one annotation and one revision. Recovery runs the same operations
in the same order — there are no separate recovery writers, which is what keeps
the two paths from drifting apart.

### An invariant that had to be relaxed

Store validation originally rejected a `current` pointer that lagged the newest
revision. That is precisely the state a crash between the immutable rename and
the pointer update leaves behind — and validation runs *before* recovery, so
the rule made that state permanently unrepairable while its own error text
promised that reopening would fix it.

A lagging pointer is now a warning, and a session advances it. A pointer naming
a revision that does not exist is still fatal.

## Effective answers

The fold is **per question**, keyed on
`(outputId, checklistId, annotatorKind, annotatorId)`.

Taking the whole newest annotation would break soft delete: judge a question,
delete it, sign off again covering only the live questions, then restore it,
and the earlier answer disappears. Folding per question keeps it, because the
row that covered it is still in the append-only log.

**Append order decides, not `createdAt`.** Timestamps tie at second resolution
and are not monotonic across a clock change; the order rows were written in is
what actually happened.

All four key components matter. Folding on annotator *kind* alone would merge
every human, and later every LLM judge regardless of prompt or model.

An item is **stale** when a live question has no effective answer, and a stale
item scores `null` — never `0`. Reporting a confident low score for something
nobody has finished judging is worse than reporting no score.

## Why validation is strict here

`lib/eval/readRun.ts` degrades one bad file and warns. That tolerance is
correct there: grading runs after every agent has been paid for, and one
unreadable record must not waste the pass.

The label store is the opposite case, so it fails loudly on: a duplicate
identity in any log, a JSONL file not ending in a newline (a torn append), an
annotation referencing an uncaptured output or a missing revision, a mismatched
checklist hash, a covered question the revision does not define, a covered
question with no answer, an answer for an uncovered question, a broken parent
chain, and a manifest from a newer schema.

## The lock

One writer at a time, as integrity protection rather than collaboration: two
sessions interleaving could race two revisions for the same version number, and
"there is only one annotator" does not stop that annotator opening two
terminals.

**A stale lock is never taken over automatically.** Guessing that a holder is
dead and stealing the store is the move that turns a crash into corrupted data,
so an abandoned lock is reported with the holder's pid and whether that process
is still running, and removing it is a person's decision.

Release proves ownership by token and only unlinks a file named `.lock`.
`safeDelete` is not used: it is project-root oriented, and a store can be
configured anywhere. Only `ESRCH` means a process is gone — `EPERM` means it
exists and belongs to someone else.

## Active time

`activeMs` is interaction time accumulated across dispatches, not wall time
since the session opened: a session paused overnight would otherwise report a
lead time of days. Only elapsed milliseconds are persisted, never a monotonic
anchor, so downtime cannot be counted. A crash loses at most the unflushed tail
since the last dispatch. There is no idle detection.

## Layering

```text
TUI          -> controller -> store facade -> private persistence modules
TUI          -> pure render helpers
controller   -> pure session reducer and selectors
store        -> pure annotation fold, status, score
```

`labelTui.ts` does not import `draft`, `checklist`, `corpus`, `capture`, `lock`
or `store`. The controller is the only module that may compose capture, drafts,
publication, annotation commits and recovery. The facade exposes no file paths,
no mutable rows and no unrestricted append — those are how ordering guarantees
get bypassed.

## What is not built yet

No judges, no agreement measurement, no calibration, no multi-annotator
reconciliation, no active learning, no pairwise UI. The schema carries
`annotator.kind` so machine judgements can share it later, and judge
annotations are intended for a separate file — a judge scores every output on
every run, and that volume must not bury the human labels it is measured
against.
