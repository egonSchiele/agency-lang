# Decision benchmark

Compare Jev, a local Laya server, and an OpenAI text model using logprobs on the same labeled inputs. This is a standalone TypeScript runner using smoltalk. It does not measure Agency compiler or checkpoint overhead.

## Build and try the input

From `packages/agency-lang`:

```bash
pnpm install --frozen-lockfile
pnpm benchmark:decisions --help
pnpm benchmark:decisions --data benchmarks/decision-models/smoke.jsonl --backend laya --dry-run
```

The command compiles its runner into `.agency-build/decision-models/` using the benchmark tsconfig. The normal Agency build and npm package exclude it.

The four authored cases in `smoke.jsonl` check the plumbing. They are too small and easy to rank models. `--dry-run` validates the input and settings without contacting a provider or needing keys.

## Input format

Each JSONL line is a case. All its questions refer to one state. Every question needs a gold label. Scores also need a numeric gold score, which may be fractional.

```json
{"id":"ticket-1","state":"Please refund my duplicate charge.","questions":{"refund":{"type":"noul","instructions":"Does the customer request a refund?"}},"gold":{"refund":{"label":"true"}}}
```

Question types follow smoltalk:

- `noul`: instructions and optional `criteria: {"false":"...","true":"..."}`. Gold labels are `"false"` or `"true"`.
- `choice`: instructions and `criteria: {"billing":"Payments and refunds","support":"Software problems"}`. Gold is one criterion key.
- `score`: instructions and an ordered array such as `criteria: ["low","medium","high"]`. Gold has a discrete `label` such as `"1"` and an expected `score` such as `1.4`. The predicted label is the most probable level; score error compares expected levels.

Gold may include a complete `probabilities` object. Brier error compares against that distribution; without it, the target is one-hot. The input parser accepts JSON strings for `questions` and `gold`, and a JSON object/array encoded in `state`, matching JSONL exports of [Typed Decisions](https://huggingface.co/datasets/LocalLLaMA/typed-decisions). Extra dataset columns are ignored. This does not read Parquet directly.

An optional `workflow` prefixes task names in the report. Keep the question type and criterion order identical within a task. Use separate files for tasks with different label spaces. Duplicate case IDs, missing labels, invalid scores, and incomplete gold distributions are errors.

## Obtain evaluation data

[UCI SMS Spam Collection](https://archive.ics.uci.edu/dataset/228/sms%2Bspam%2Bcollection) is a useful first binary task. Download and unzip its archive, then convert the tab-separated `SMSSpamCollection` file:

```bash
pnpm benchmark:decisions import-sms /path/to/SMSSpamCollection sms.jsonl
```

The importer preserves message text and maps `spam` to true and `ham` to false. Pick a held-out sample once with `--limit` and `--seed`, then use exactly those settings for each backend. Do not tune prompts on that sample. SMS has an imbalanced label distribution; read macro-F1 alongside accuracy.

[BANKING77](https://github.com/PolyAI-LDN/task-specific-datasets) provides a harder intent-classification task. Jev/Laya can accept its full label set. This runner's logprobs adapter is limited to 20 options, so it refuses a 77-way question. Do not silently discard categories to make it fit.

Typed Decisions exercises several questions per state, including ordinal scores. Its gold distributions were generated by a teacher model: a high score means agreement with that teacher. Use its test split. Report Laya's `typed-decisions` checkpoint separately from general models because it was trained for those workflows. Dataset versions can change; retain the exact JSONL used. Each run records its SHA-256 and selected IDs.

## Compare latency

Use the same dataset, seed, limit, and repeats for each command. The default mode sends one question per request and runs one case at a time. Timings include HTTP overhead and text generation through the complete reply.

```bash
export TYPESAFE_API_KEY='your-key'
pnpm benchmark:decisions --data sms.jsonl --backend jev --limit 500 --repeats 3 --out jev.jsonl

# Start laya-serve separately; its installation is outside this runner.
pnpm benchmark:decisions --data sms.jsonl --backend laya --limit 500 --repeats 3 --machine local-laya-server --out laya.jsonl

export OPENAI_API_KEY='your-key'
pnpm benchmark:decisions --data sms.jsonl --backend logprobs --model gpt-4o-mini --limit 500 --repeats 3 --out text.jsonl
```

Jev through OpenRouter uses `--model jev-1.13 --base-url https://openrouter.ai/api` and the OpenRouter key in `TYPESAFE_API_KEY`. Laya defaults to `http://localhost:8000`, with `LAYA_BASE_URL` and `LAYA_API_KEY` overrides. Its default key is the dummy value `unused`. Pin a model/checkpoint version when comparing runs.

The text adapter uses OpenAI Chat Completions. It requests temperature zero, at most four output tokens, and 20 token alternatives. Choose a model supporting these parameters; unsupported settings produce an error. Each question gets a fresh two-message conversation containing the state and question, with no gold labels or previous answers. The adapter disables OpenAI SDK retries, and the runner does not retry failed calls.

Each option gets a letter code. The response must contain one answer token matching that code; otherwise the case records an error. The adapter adds probabilities of returned token spellings that decode to the same code. It records the probability mass assigned to valid labels. If every label appears, it normalizes over the returned label tokens. These are probabilities conditional on that candidate set, not a complete vocabulary distribution. If any label is missing from the top alternatives, it leaves the distribution absent and excludes that prediction from Brier/expected-score metrics. Label accuracy still counts. Check `probabilityCoverage` and `meanLabelMass` before comparing Brier numbers.

## Compare throughput and batching

```bash
pnpm benchmark:decisions --data cases.jsonl --backend jev --mode throughput --concurrency 4 --batch-size 64 --out jev-throughput.jsonl
pnpm benchmark:decisions --data cases.jsonl --backend laya --mode throughput --concurrency 4 --batch-size 64 --out laya-throughput.jsonl
pnpm benchmark:decisions --data cases.jsonl --backend logprobs --mode throughput --concurrency 4 --out text-throughput.jsonl
```

Batch size is questions **about the same state** per decision request, capped at 64. Different cases always remain separate requests. The text adapter sends one question per request, sequentially within each case. Concurrency counts cases. On binary SMS examples, each case has only one question, so increasing batch size cannot help. Use a multi-question dataset to measure that benefit.

The header records settings, client hardware, endpoint, model, and case IDs. For a local checkpoint, pass `--checkpoint-sha256` with the SHA-256 of the served `model.safetensors` file. The runner validates 64 hexadecimal characters and saves the lowercase value as `metadata.checkpointSha256`; it is null when omitted. This is operator-supplied provenance, not a verification of what a remote server loaded. Offline summaries preserve it. `--machine` should identify the Laya server's hardware if it runs elsewhere. Compare one backend at a time to avoid local resource contention. Treat hosted latency as end-to-end service latency, not accelerator speed.

One warmup case runs by default. It may include local model loading and is recorded separately. A failed warmup stops the run. Warmups and repeated inputs may warm provider caches; the report is a warm-workload measurement. Use `--warmup 0` and a fresh server to investigate cold starts separately.

## Results and offline summaries

The output file must not exist. The runner saves a JSONL record after every measured case, including partial responses and failures. Saved smoltalk results retain the usage, cost, model identity, and token probabilities available from that client. For text models, smoltalk reports the requested model name rather than the version resolved by the server; use a pinned model name for reproducible comparisons. Thrown request errors retain question IDs, timing, and HTTP status when available. It never writes API keys. Keep these files private if the replies contain sensitive material. A completed run ends with a wall-time record; an interrupted run can still be summarized, but has no throughput result.

```bash
pnpm benchmark:decisions --summary jev.jsonl > jev-summary.json
pnpm benchmark:decisions --summary laya.jsonl > laya-summary.json
pnpm benchmark:decisions --summary text.jsonl > text-summary.json
```

The report contains:

- Accuracy and macro-F1 by workflow/question; failed answers count against accuracy and recall. `successfulAccuracy` and `coverage` show the distinction.
- Confusion counts and failed-answer counts for every true label.
- A 95% percentile-bootstrap accuracy interval, resampling whole cases across repeated trials. With fewer than two distinct cases it is null. Very small or all-correct samples can give misleadingly narrow intervals.
- Brier error, defined as the sum of squared probability errors across labels, averaged across complete distributions. Soft gold measures agreement with the teacher. Compare the same tasks and inspect probability coverage.
- Mean absolute error for ordinal expected scores and its coverage.
- Successful-case p50/p95/mean latency, failed-case median latency, and completed decisions per measured wall-clock second. A case with five questions has five decisions, so compare identical case structures. Warmups are excluded.

The runner reports each model independently. For close rankings, inspect paired errors on the same case IDs instead of declaring a winner from overlapping averages. No paid model calls are part of its automated tests.
