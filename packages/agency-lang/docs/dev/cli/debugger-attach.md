# Attaching the debugger to a running program

The design is `docs/superpowers/specs/2026-10-20-attach-to-a-running-program.md`. This doc records what shipped and the parts that are easy to get wrong. The runtime half, a driver installed on a program something else is running, is the section "A debugger installed on a running program" in `debugger.md`; this doc is the channel, the trigger, and the socket. The command is `agency debug --attach [pid]` (`lib/cli/attach.ts`); the user's view is in `docs/site/cli/debug.md`.

## The pieces

- `lib/debugger/attach/channel.ts`: the `Channel` type (`send`, `onMessage`, `onClose`, `close`) and `memoryChannelPair()` for tests.
- `lib/debugger/attach/protocol.ts`: the messages, as zod schemas, with a compile-time check that the hand-written command and response schemas match the types they check (`SameShape`), so a command added to `DebuggerCommand` without a schema line fails to compile. `finished` carries `error` when the run ended by throwing, and its `value` is optional: a node that returns nothing has none, and JSON drops a key whose value is undefined, where zod 4 would require the key. The memory pair used in tests delivers messages as JSON for the same reason. One `request` per `DebuggerIO` method that expects an answer, with an id the `reply` carries back; one `notice` per method that returns at once (`log`, `setMode`, `setOverrides`, `appendStdout`, the spinner); and three that are not methods: `hello` from the run when a debugger connects, `finished` when the program ends, and `refused` when a debugger is already attached. There is no detach message: closing the channel, from either side, is the detach. `REPLY_SCHEMAS` says what each request's reply must carry. `client` is the first message a connection sends, saying what it is (`terminal`, `cli`, or `probe`), and `status` is what a probe gets back.
- `lib/debugger/attach/channelIO.ts`: `ChannelDebuggerIO`, the run side's `DebuggerIO`. A call waiting for a reply when the channel closes is rejected with `DebuggerDetached`, which the attached driver treats as `continue`. A reply that carries the UI's error, or a result that fails its method's schema, ends the session the same way, with one line on the program's stderr saying why: a program must never fail because its debugger did, and before this rule a terminal UI that hit a bug while drawing a checkpoint took the agent down with it.
- `lib/debugger/attach/serveIO.ts`: `serveDebuggerIO(channel, io, events)`, the UI side, which answers each request with the matching call on a real `DebuggerIO`, the terminal UI or a scripted one in a test. `checkpointFromWire` sets an empty function-ref registry before reviving, because the debugger's process loads no compiled module and only a module sets one; a function value in a frame then revives to the stub a registry miss gives, which is all a UI that shows the state needs.
- `lib/debugger/attach/lineChannel.ts`: a channel over a Node socket, newline-delimited JSON with a 64 MiB cap per message. A message is kept as the pieces it arrived in and joined once at its newline, since scanning the whole buffer on every chunk made a 60 MiB message take half a minute; the cap is checked per line, and per partial line as it grows. A message over the cap, sent or received, closes the session with a line on stderr. `close` ends the socket and destroys it once the writes have gone out, with a short fallback, because destroying right after `end` threw away a `finished` message over about 8 KB.
- `lib/debugger/attach/registry.ts`: the sessions directory and its records.
- `lib/debugger/attach/sessionRules.ts`: the rules of a session as one pure function, `step(state, event)`, which returns the new state and a list of effects (send this message to this party, close this party, deliver this reply to the driver, start or clear the lease, log a line, end the session). Who may join, who is refused, what a joining party is sent, which reply answers the driver's request, when the lease fires, and when the session ends are each one case of it, and `sessionRules.test.ts` is a table of them. See "A session with parties" below.
- `lib/debugger/attach/sessionChannel.ts`: the adapter. It implements `Channel`, so `ChannelDebuggerIO` speaks on it as it would on a socket, holds the state, feeds every message, connection, close, and timer firing through `step`, and applies the effects to the parties' channels. The only file of the session with a timer in it.
- `lib/debugger/attach/server.ts`: `openSession`, which is all of attaching: a session channel, a `ChannelDebuggerIO` on it, a driver, `hello`, and the driver installed; `attachOverChannel`, which opens a session with one channel as its terminal, for tests on a memory pair; and `startAttachServer`, the socket around it. The server takes the functions as a getter and reads it when a debugger connects, so the context running then is the one attached to; a TypeScript program can have started another module's node since the signal arrived.
- `lib/runtime/attachedDebugger.ts` also holds `attachFunctionsFor(ctx)`: the four functions a driver takes, bound to a context, for the server that runs inside the program and has no module to ask. They are bound in the runtime that owns the context and handed to `registerAttach`, because the `#platform` file can be a different copy of the runtime than the one the program imported: a test loads the program's copy through vite and the platform file through Node, and a copy that did not load the program's modules fails the fingerprint check on resume.
- `lib/runtime/platform.node.ts`: `registerAttach`, called by `runNode`.

## What crosses the channel

A checkpoint crosses as `checkpoint.toJSON()` run through `nativeTypeReplacer`, the way `debugStep` prepares the `onCheckpoint` payload, and comes back through `nativeTypeReviver` and `Checkpoint.fromJSON`. The rewind selector and the checkpoints panel are sent the whole window of checkpoints, not summaries: both show the state at each checkpoint as the selection moves, so a summary would not do. They are sent only when the person opens the panel, and the per-message cap is sized for them. `DebugStopData`, `GuardTripData`, `DebuggerCommand`, and `InterruptResponse` are plain data already, and so is the list of `BusyEntry` the `setBusy` notice carries, what the program is waiting on (see "What the program is waiting on" in `debugger.md`); the UI side takes the list as sent. The `pause` message carries nothing: it is the one message the UI side sends unprompted, when the person presses `s` or `n` while the program runs, and the run side turns it into stepping mode for the next statement.

## Registration

`runNode` calls `registerAttach({ ctx, nodeName, host, functions })` on every node run, with the host the run uses (the invocation's when it names one) and the driver functions bound to the context. The record and the signal listener are written once per process, by the first node run; a later run only makes its context the one a debugger attaches to, since a TypeScript program that imports two Agency modules, or a test worker that runs many fixtures, has several contexts in one process and the one running now is the one a person attaching now means. The call returns at once when: the host is not the Node host, so a memory host in a test writes nothing; the code runs in a worker thread, whose `process.on` never sees a signal while the main thread, with no listener, would be ended by it; a debugger is already installed, so `agency debug` does not register its own process and a second debugger cannot attach over the first; or the process is an IPC child of a parent Agency program (`isIpcMode(host)`, which reads `AGENCY_IPC`, set by the parent; a test worker also has an IPC channel to its runner, so the channel alone would not do), which the listing leaves out. `runNodeForServe` does not call it, so a serve never registers: one serve process runs many invocations at once and one shared `DebuggerState` would stop them all. A directory that was refused is remembered, so a program that runs a node in a loop pays the check and the log line once.

Registering writes `<pid>.json` in the sessions directory and installs a `SIGUSR2` listener. The listener is kept in one slot on `process` (a symbol), and every registration claims the slot: a process can hold more than one copy of the runtime (a test worker re-evaluates modules per file; a program can have the package twice under `node_modules`), each with its own attach target, and two listeners would start two servers racing for one socket, the loser answering with a context whose modules it cannot see. Claiming on every registration, not only the first, means copies that register A, B, A leave A's listener in place. Node reserves `SIGUSR1` for its own inspector, whose port any local user can reach, so Agency does not touch it; `nodemon` restarts a child with `SIGUSR2`, which a program under `nodemon` then no longer honours. The record holds the pid, the program path from `process.argv[1]`, the first node run, and the process start time as `performance.timeOrigin`, read without a child process (not from `process.uptime`, whose monotonic clock stops during a suspend). A sessions directory that cannot be used is logged under `DEBUG` and the run goes on without attach: a program must never fail because it cannot be debugged. The record and the socket are removed in `host.system.onExit`.

## A session with parties

A terminal debugger's connection used to be its session: `attachOverChannel` built a driver on the channel and detached when the channel closed. An agent's commands are separate processes, so for `agency debug session` (spec: `docs/superpowers/specs/2026-10-20-agent-debug-session.md`) the session had to outlive the connection that opened it. So the run holds the session, and a connection is a party on it. `openSession` builds the driver once, on a `sessionChannel`; connections are admitted to that channel with the kind their `client` message gave. A `terminal` is a party whose close ends the session, as before. A `cli` visit opens the CLI's hold on the session the first time and joins it after; a visit that closes leaves the driver's request pending, and the next visit is sent `hello`, the recent activity lines as `log` notices, the last `render`, and the pending request, so it picks up where the last one left off. A `probe` is sent `status` and closed, with no driver installed when no session is open, so a listing costs a run nothing.

The lease: a program must never wait on a debugger that is not there, and an agent can crash or forget, so the hold lasts ten minutes from the last visit's close (`LEASE_MS`). When it runs out the run logs one line on stderr and the session ends: the pending request is rejected with `DebuggerDetached`, which the driver answers as `continue`, and the program runs on at no cost. The timer is `unref`ed, so a held session never keeps a finished program alive. With no socket of its own to hold while a request is pending, the session's `keepAlive` refs the server instead.

The program's end while the hold has no visit is kept (`finished` in the state) and handed to the next visit, which is then closed; the driver comes off the program at once either way. In this version one terminal and one CLI hold do not share a run: a terminal is refused while a hold is live, and a visit is refused while a terminal is attached, with the reason naming the other. Letting both on one run, either driving, is the next PR of the spec.

The one thing the memory pair does differently from a socket showed up in `held.test.ts`: it delivers a message sent just before a close after the close listeners ran, so a visit that replies and closes in the same tick has its reply dropped as a message from a party no longer on the session. A socket delivers the data first. The test waits one turn between the two.

## The sessions directory

`~/.agency/debug-sessions`, or `debug-sessions` under `AGENCY_HOME`, which test setup points at a temporary directory. `~/.agency` is Agency's own per-user directory (`agencyHomeDir`), not the agent home: `~/.agency-agent` belongs to the built-in `agency agent`, and attach is for any program.

Whoever can connect to the socket can do what the program's owner can do, so the directory is treated as a credential. `ensureSessionsDir` creates it with mode `0700` and refuses it unless the current user owns it and no group or world bits are set. The run checks at registration and again in `startAttachServer`, right before `listen`, since the signal can come hours after registration and the directory can have been replaced in between; the CLI checks on every use. That check is what the safety argument rests on. The socket is also `chmod 0600` after `listen`, a second layer with a short window at the umask's mode, which is why the directory check comes first. `fs.mkdirSync` applies a mode only to a directory it creates, so a directory left by an earlier build keeps whatever mode it had, and the check tells the person to `chmod 700` it. A record is written with `wx` after removing the path, so a symlink left at `<pid>.json` is replaced rather than followed, and a record is read only when the pid inside matches its file name, so a hand-edited file cannot point the CLI at another process.

## The socket

`startAttachServer` listens on `<pid>.sock`, removing a leftover socket at its own pid's path first (a run that exited through a signal handler leaves one, and a reused pid would hit `EADDRINUSE` on it), and refuses on Windows and on a path over 104 bytes, the limit on macOS and the BSDs. Every failure, including a directory at the socket's path that the removal cannot take, comes back as `unavailable` and one line on stderr; the signal listener also catches a rejection from the call, since an unhandled rejection ends a Node program as a throw would. The server and every accepted socket are `unref`ed, so an open session never keeps a finished program alive; the run side's `ChannelDebuggerIO` `ref`s the socket while a request is pending (`Channel.keepAlive`), because a program stopped at a debug stop is waiting on the debugger's answer and may hold no other handle, and with the socket unreferenced Node would exit with code 13, an unsettled top-level await. The end-to-end test in the command's PR found that. The first connection gets `hello` and a driver; a second while one is attached gets `refused` with "already attached since <time>" and is closed, since Node cannot read the peer's pid from a Unix socket. When the channel closes for any reason the driver detaches, and when the program finishes while attached the run sends `finished` and closes; a paused checkpoint, from the caller's own pause signal during a leg the debugger ran, is a suspension and not the end, so the session stays. The driver's last render, at the end of the program, is sent and not waited for: at a stop, waiting on the debugger is what the person asked for, but a debugger suspended with Ctrl-Z must not keep a finished program from exiting.

## The command

`agency debug --attach` with no pid lists the records in the sessions directory after removing the stale ones, in the spec's table, with a program under the current directory shown relative to it. With a pid it checks the directory the way the run does, reads the record, and checks the live process before it sends anything: a run that crashes leaves its record behind, and the operating system may later give its pid to an unrelated process, which `SIGUSR2` would kill. First `processState`, the `kill(pid, 0)` probe the registry's stale sweep uses: a pid with no process has its record removed. Then the start time from `ps -p <pid> -o lstart=`, run in the C locale, since `lstart` is otherwise in the user's language and `Date.parse` reads only English, and in UTC, parsed as UTC, since a local wall time has no zone and the repeated hour on the night the clocks go back would read an hour early. The check has a limit on each side: a live process that started more than a minute after the record was written is a stranger that got the pid after the registered process exited, and the record is removed; one that started after it by more than two seconds (the resolution of `lstart`) but less than a minute is refused with the record kept, because on Linux `lstart` is boot time plus ticks and the kernel moves boot time when the wall clock is stepped, so an NTP step after the program started makes a running program look that much younger; one that started up to five minutes before the record is the process itself, started by a wrapper script that did some work and then `exec`ed node, which keeps the wrapper's start time; one older than that is a stranger that had the pid all along, which a record from another machine or pid namespace names by accident (a home on NFS, a container that mounts `~/.agency`), so the attach is refused and the record left alone, since it is not this machine's to remove; the message says what to do when it is this machine's program after all (a wrapper that ran for minutes before it): remove the record file. A `hostname` in the record, so that another host's records are never signalled, removed, or listed, is listed in `debugger-future-work.md`. When `ps` cannot answer (missing in a slim container, BusyBox without `-o lstart`), the attach is refused with the reason and the record kept. Then the signal, a connect that retries for two seconds while the program opens the socket, and `serveDebuggerIO` on the terminal UI. A refusal goes to stderr; the listing goes to stdout. With the terminal UI, stdin must be a terminal, checked before the signal: a UI that failed at its first key would end the program's session right after it opened.

While attached, the UI's status line names the pid and program, the command bar says `(q)detach`, and only `q` detaches: `escape` maps to `quit` in the keymap and would detach by accident, so it is ignored. `q` closes the channel, which is the detach on the run side; the run answers a stop it was waiting at with `continue`. Keys typed while the program runs are queued by `TerminalInput` and acted on at the next stop. Ctrl-C arrives as a key in raw mode, at a stop and while the program runs, since the UI reads keys while the program runs for the pause key; `DebuggerUI.dispatch` exits the process with 0 before the `SIGINT` that `TerminalInput` also raises is delivered. Either way the socket closes, which is the same detach. The command exits 0 when the channel closes: "Program finished" or "Program threw" when the run sent `finished`, "Detached from pid N" when `q` was pressed, "The connection to pid N closed; the program may have exited" otherwise, since a program that was killed closes it too; and 1 on a refusal, the program's "already attached" refusal included, which goes to stderr like the command's own.

The `--attach` flag and a file contradict each other and are refused (`attachTarget` in `lib/cli/debugFlags.ts`), as is a pid that is not a run of digits, and so is any other flag typed with `--attach` (`--policy`, `--rewind-size`, `--trace`, and the rest): the program keeps the options it was started with, and a flag parsed and dropped would look as if it had worked. The flags the person typed are told from defaults by commander's `getOptionValueSource`.

## Tests

`sessionRules.test.ts` (the table: every rule of `step`, as a state and an event in and the effects out), `held.test.ts` (the driver and the adapter on a memory pair: the program stays stopped across visits, the next visit picks up the pending request, three reading visits move nothing, the lease, the program ending with no visit connected, a terminal refused while held), `channel.test.ts` (the memory pair and the line channel on a real socket: the cap, two messages in one chunk, and the last message before a close), `attach.test.ts` (a scripted IO on a memory pair, including a UI that throws and a reply of the wrong shape, a checkpoint with a function value rebuilt with no registry, and the real path: `runNode` registers the test process, the signal handler is called the way the signal would call it, and a client on the socket drives the program), `registry.test.ts`, `server.test.ts` (including the getter naming a second context), and the `registerAttach` cases in `lib/runtime/platform.test.ts`. The unit test run points `AGENCY_HOME` at one temporary directory, made in `lib/debugger/attach/vitest.globalSetup.ts` before the workers are forked and removed when the run ends, by the teardown and by `exit`, `SIGINT`, and `SIGTERM` hooks for a Ctrl-C, which pnpm and npx forward a second time after vitest's own once-only handler is gone (a per-worker setup file could not remove its directory: vitest ends a forked worker without an `exit` event), because every program a test runs on the Node host registers, and the real `~/.agency` must never see a test's records. Every child `agency test` starts, for a `.agency` case or a `test.js`, gets a throwaway `AGENCY_HOME` of its own. `lib/cli/attach.test.ts` (the flag combinations, the listing, the `lstart` parse and the C-locale `ps` call, the start-time check in both directions with a stubbed `ps`, and a real session: a fixture compiled into `.agency-tmp` and started with `node`, listed, attached to with a headless `DebuggerUI`, stepped, and detached from with `q`, after which the child exits 0).
